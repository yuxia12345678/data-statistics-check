## 一、需求理解与拆解

题目的实质不是"会不会算这些统计"，而是三件事同时成立：

1. **口径统一**——统计逻辑不能依赖操作人经验，必须固化在代码里，换人换机器结果一致；
2. **动态可更新**——所有统计单元格必须是公式，改一行明细，全表联动；
3. **格式合规**——8 张表、表名一字不差、金额千分位 3 位小数、百分比 2 位小数、
   对齐/斑马纹/边框/列宽/冻结逐项达标。

其中 (2) 和 (3) 是最容易失分的地方：让大模型逐格设置格式，每次跑出来都不一样；
而"禁止硬编码"与"评审要能读到数值"之间存在技术冲突（见第五节）。
因此整体设计原则是：**把全部确定性工作沉到脚本，SKILL.md 只负责让模型调脚本，不让它自由发挥。**

## 三、口径确定过程

题目正文没有定义"合同数""回款率""未回款占比"的分子分母，也没规定任务1 的排序。
这些是分值最集中的地方，猜错就整表错。做法是**用《附件2-示例》反算**：
示例文件是主办方产物，它的每个数值都是一条口径证据。

### 3.1 合同数：排除法确定

对同一分组计算三种候选口径，与示例值比对：

| 分组 | 示例值 | 明细行数 | 组内不同合同号 | 合并表中该维度值的行数 |
|---|---|---|---|---|
| 区域·华南-海南 | 29 | 29 | **29** ✓ | 14 ✗ |
| 部门·三部 | 95 | 104 ✗ | **95** ✓ | 42 ✗ |
| 账龄·1-2年 | 246 | 322 ✗ | **246** ✓ | 146 ✗ |
| 客户分类·事业单位 | 120 | 131 ✗ | **120** ✓ | 65 ✗ |

结论：**合同数 = 该分组原始明细行中不同合同号的个数**（去重计数）。
区域维度恰好"明细行数 = 去重数"，若只看区域会误判为明细行数，
因此用部门/账龄/客户分类三个维度交叉排除。四维度 55 个分组全部吻合。

### 3.2 未回款占比：分母是全局总合同金额

`区域·华南-海南：11774.220 / 911876.017 = 0.01291208429709145`
`账龄·1-2年：  78928.404 / 911876.017 = 0.08655606960655485`

两处独立验算均与示例值吻合到小数点后 16 位。分母是**全局总合同金额**，
不是本组开票金额、也不是全局开票金额。

注意任务2 的「占比」分母与任务3 不同：题目正文明确写"占**全部总未回款金额**的比例"，
即全局总开票未回款（210976.108）。两处分别按各自依据实现，已在 SKILL.md 与
`references/口径与公式规范.md` 中并列说明，避免被当成同一口径。

### 3.3 整体回款率

`区域·华南-海南：5325.631 / 23982.43 = 0.2220638609181805` ✓
即 **组内回款合计 ÷ 组内合同金额**。

### 3.4 任务1 排序

示例「同合同号合并汇总」首行是 `HT20250220`（合同金额 16854.085），
而源文件首个合同号是 `HT20250101`。逐一比对四种候选排序后确认：**按合同金额降序**。
463 行的合同号与合同金额逐行比对，匹配 463/463。

> 🔄 **2026-10-03 变更**：按需求改为**按合同号升序（从小到大）**，不再沿用示例的合同金额降序。
> 实现见 `stat_engine.get_contract_list()`，自检见 `verify.py` 的 R7-合并；
> 该差异已登记在 `references/与示例文件的差异.md`。

### 3.5 口径落地为公式

| 指标 | 公式形态 |
|---|---|
| 分组求和 | `SUMIF(维度区间, 本行维度值, 数值区间)` |
| 分组计笔数 | `COUNTIF(维度区间, 本行维度值)` |
| 分组去重计数 | `SUMPRODUCT((维度=本行维度)/COUNTIFS(合同号,合同号,维度,维度))` |
| 全表去重计数 | `SUMPRODUCT(1/COUNTIF(合同号,合同号))` |
| 组内第一条非空值 | `IFERROR(INDEX(值区间,MATCH(1,INDEX((合同号=键)*(值<>""),0),0)),"")` |
| 比率 | `IF(分母=0,"",分子/分母)`（零分母输出空值，不把未知包装成 0） |

全部区间绝对引用、表名加单引号，首末行由程序探测后拼入，不写死 1002。

```
data-statistics-check/
├── SKILL.md                    # 【执行依据】触发条件、目录结构、执行命令、硬性规则、口径表、验收清单、故障排查
├── README.md                   # 面向人的项目说明（非执行依据）
├── requirements.txt            # 依赖：openpyxl + pandas + numpy
├── .github/agents/             # contract-data-statistics.agent.md（Agent 封装）
├── 输入/                        # 待处理源表（附件1-合同开票及回款核对表.xlsx）
├── 运行成果/                    # 交付产物三份：结果 xlsx + 运行回执.json + 自检报告.json
├── config/
│   └── contract_repayment.json # 唯一业务配置：表名/指标/口径/样式/排序，改口径只改它
├── references/
│   ├── 口径与公式规范.md         # 每条口径的定义、公式、验证证据
│   ├── 样式规范.md               # 每个样式参数的取值与依据
│   ├── 与示例文件的差异.md       # 差异清单、证据、取舍与切换方式
│   └── 构建过程文档.md           # 本文
├── _recovery/                  # 历史快照（含已下线的 analyze 链路 pathA/ 等），确认后可删
└── scripts/                    # 8 个文件，全部为执行路径所需
    ├── run_skill.py            # 入口：--config --input [--output-dir] [--report]
    ├── stat_engine.py          # 引擎内核：按 JSON 配置构建 8 张工作表
    ├── formula_builder.py      # Excel 公式生成器（限定数据区间）
    ├── excel_styler.py         # 统一美化（表头/斑马纹/边框/列宽/冻结/条件格式）
    ├── config_validator.py     # 配置 schema 校验（含 8 张表名严格匹配）
    ├── agg_strategy.py         # 通用聚合策略注册表（sum / nunique / …）
    ├── cached_values.py        # 公式缓存值 XML 注入（由 stat_engine 调用）
    ├── verify.py               # 交付前自检 46 条断言（期望值同样读取该 JSON）
```

分层理由：`config/contract_repayment.json` 集中全部可变业务项（表名、指标、口径、排序、样式），
改口径或改样式不需要动业务代码；`formula_builder.py`（只拼公式）与 `excel_styler.py`（只落地样式）
分离，公式正确性和格式合规性可以独立排查；`config_validator.py` 在生成前拦截配置错误，
`agg_strategy.py` 提供可扩展的聚合策略注册表；`verify.py` 不 import `stat_engine.py`，
从源文件重新算一遍期望值（期望值常量**同样派生自该 JSON**），形成
"源事实 → 产物"的独立验证链，而不是用生成逻辑自证。

**为什么只有一个 Skill**：任务是单一输入 → 单一输出的流水线，
拆成多个 Skill 会增加模型编排次数、依赖交叉引用和中间态传递，
而题目明确"缺失依赖导致 Skill 无法执行将直接判定任务失败"。
因此采用"一个 Skill + 内部文件分层（渐进式披露）"：SKILL.md 保持薄，
细节规则沉到 references/，实现沉到 scripts/。

## 五、关键技术难点与解决

### 难点1：「禁止硬编码」与「评审能读到数值」的冲突

openpyxl 写公式时只写 `<f>`，不产生缓存值 `<v>`。这样的文件用 Excel 打开没问题，
但被 `openpyxl(data_only=True)` 或 pandas 读取时全是 `None`——评审若用程序核对数值，
会认为整张表是空的。

**解决**：保存后用纯 Python 直接改写 OOXML，为每个含 `<f>` 的单元格补上 `<v>`，
并设置 `calcPr/@fullCalcOnLoad="1"`（Excel/WPS 打开时整簿重算）。
产物同时具备真实动态公式和可读数值，且**不依赖 LibreOffice 等外部中间件**
（题目明确不提供额外环境资源）。本次 6024 个公式单元格（题目原版数据集为 6004），
6024 个缓存值全部注入。

Python 计算结果只用于两件事：注入缓存值、供 `verify.py` 复核。
两条路径独立实现，互不复用。

### 难点2：如何证明公式本身是对的，而不是缓存值自证

第一次交叉验证时把带缓存值的文件交给 LibreOffice 转换，结果 19611 格全部"一致"——
这个结论是**假的**。用一个反向测试戳破了它：故意把「区域统计」C3 的缓存值改成 `1.0`，
LibreOffice 转换后仍是 `1.0`，说明 `--convert-to` 默认不重算，只是原样搬运缓存值。

**正确做法**：先剥离全部缓存值（该轮为 6004 个），再交给 LibreOffice 从零实算，
然后与 Python 独立计算结果逐格比对。结果：19611 个单元格，**0 处不一致，0 处空值**。
这才真正验证了 `SUMIF`、`SUMPRODUCT+COUNTIFS` 去重计数、
`INDEX+MATCH` 数组技巧（无需 Ctrl+Shift+Enter）在真实表格引擎中的行为。

> ⚠️ **该验证的边界**（2026-10-03 补记）：那一轮数据集「未回款原因分类」全空（任务2 无数据行），
> 四维度列的取值也不含空白，因此**未覆盖“分组列存在空白单元格”**的情形；
> 分组去重计数在那里会因条件为空白而 `0/0` → `#DIV/0!`。见难点6。

### 难点3：「原始数据」原样复制 vs 全工作表统一美化

题目两条硬性要求直接冲突：注意事项(1) 说"不得修改原始数据的单元格格式，任何改动均视为违规扣分"，
美化规范说"所有输出工作表必须统一格式标准，全程合规无遗漏"。

**解决**：区分"数据本体"与"展示层"。
值、行列顺序、数字格式、第 1 行内容一律零改动（`verify.py` 的 R2a–R2d 逐格比对源文件）；
填充色、字体、边框、对齐、列宽、冻结属于统一美化，予以叠加。
实现上不走"pandas 读入再写出"（那样格式和日期必坏），而是**直接在源工作簿副本上把
Sheet1 改名为「原始数据」**，再新建其余 7 张表——值和格式天然 100% 一致。
「原始数据」不做任何行列增删、不重排、不改数字格式，美化仅叠加在展示层。

> 🔄 **2026-10-03 变更**：改为**「原始数据」零美化**（只改表名）：填充 / 字体 / 边框 /
> 对齐 / 列宽 / 冻结窗格也一律不动 —— 注意事项(1) 的"任何改动均视为违规扣分"覆盖
> 单元格格式，此前叠加斑马纹 / 表头底色 / 边框 / 列宽 / 冻结的做法已废弃。
> 开关：配置 `style_setting.raw_beautify`（默认 `false`）；`verify.py` 的 R2a–R2d
> 已升级为**全表逐格**比对（值 / 数字格式 / 填充·字体·边框·对齐 / 行数·列数 / 列宽 / 冻结）。

### 难点4：示例文件与题目正文 9 处不一致

包括工作表顺序、金额小数位（3 位 vs 2 位）、日期与分类字段对齐、边框（仅水平 vs 四边）、
条件格式（要求有 vs 实际 0 条）、维度表表头文字、原始数据是否重排、公式有无、空值填充。

> 🔄 **2026-10-03 变更**：其中「工作表顺序」已统一——`统计总览` 由第 4 位改为**排最后**
> （与示例一致），故实际仍存在 8 处差异；其余条目未变。
>
> 🔄 **2026-10-03 变更（条件格式）**：任务2 分类列的差异化柔和背景条件格式**改为不启用**
> （配置 `style_setting.reason_soft_cf = false`）——该列一旦上色就与同行斑马纹不一致，
> 用户选定改为与示例一致（0 条规则）。代码、调色板、断言均保留，改配置即可恢复。

**解决**：做成双 profile，一个参数整体切换，默认以题目正文为准（`spec`）。
两套 profile 的产物都能通过 `verify.py` 46 项自检。
差异逐条记录在 `references/与示例文件的差异.md`，含证据与切换方式。

其中示例文件的三处判定为**缺陷而非规范**，未跟随：
开票日期整列 `#VALUE!`、空值被填成「未填写」、全文件无公式。
另有一处旁证：示例的列宽明显失真（「回款率」列宽 28.29 而显示内容只有 6 字符），
推断其生成流程按公式字符串长度算了列宽——本实现按单元格**最终显示值**计算列宽，避免同一问题。

### 难点5：列宽自动适配（中文全角）

`显示宽度 = Σ(全角计2, 半角计1)`（`unicodedata.east_asian_width in ('W','F')`），
`列宽 = clamp(max(表头, 各数据行) + 3, 8, 40)`。
参与计算的必须是格式化后的显示值：金额按 `#,##0.000` 渲染、比率按 `0.00%` 渲染，
不能是公式文本，也不能是原始浮点数。

### 难点6：缓存值正确 ≠ 公式正确（两个缺陷相互掩盖）

**现象**：换成含 4 个「未回款原因分类」的数据集后，该表首行以外的分类底色全部丢失，
「涉及合同数」列显示 `#DIV/0!`。而当时的 44 项自检 **全部通过**。

**根因（都是重构回归，`_recovery/pathA` 里的原始实现是对的）**：

| 缺陷 | 错误写法 | 正确写法 | 后果 |
|---|---|---|---|
| 条件格式锚点 | `$B4="需求不满足"`（分类自己那一行） | `EXACT($B3,"需求不满足")`（**区间首行**） | Excel 以 sqref 左上角为基准做相对行偏移，判断第 4 行时 `$B4` 被偏移成 `$B5` → 除首行外一条规则都不命中，露出斑马纹 |
> 🔁 **2026-10-03 后续**：该列条件格式已按用户要求**关闭**（`reason_soft_cf=false`），
> 改为与同行一致的斑马纹（见上「变更（条件格式）」）；下表保留的是公式坑本身的技术记录，
> 启用时仍然适用。另外 `verify.py` **R11 已升级为逐格斑马纹断言**，
> 不给“某列偷偷单独上色”留空间。| 去重计数条件 | `COUNTIFS(合同号,合同号&"",维度,维度)` | `COUNTIFS(合同号,合同号&"",维度,维度&"")` | 裸区间里的空白单元格被 Excel 当作 `0`，分母 0 → `0/0` → `#DIV/0!` |

**为什么 44 项自检漏掉了**：缓存值由 pandas 独立算出并注入 `<v>`，**永远是对的**；
而当时所有数值类断言读的都是缓存值。缺陷只在 Excel/WPS 打开重算（`fullCalcOnLoad="1"`）时才暴露，
属于“自证链”之外的盲区。

**收口**（两道新断言，均为回归防护）：

- `verify.py` R17：每条条件格式规则的公式必须是 `EXACT($<列><区间首行>,…)`，锚点行 ≠ 区间首行即失败；
- `verify.py` R18：遍历所有生成公式，`COUNTIF/COUNTIFS` 的**条件参数不得是裸区间**（须带 `&""`）。

**教训**：只要产物里的数值同时有“公式”和“缓存值”两个来源，就必须区分
“值断言”（读缓存）与“公式断言”（读文本），后者才能覆盖重算型缺陷。

## 六、验证体系

三道独立验证，全部通过：

| 验证 | 方法 | 结果 |
|---|---|---|

## 八、已知限制与登记的例外

1. **公式化例外（1 处）**：合并表的「未回款原因分类」列写入的是去重拼接后的文本结果，
   不是公式。原因：该操作是文本聚合，Excel 无非动态数组的稳定写法
   （`TEXTJOIN+UNIQUE+FILTER` 依赖 Excel 365，LibreOffice 与旧版 Excel 不兼容，评审环境不可控）。
   该列是文本而非数值，题目"禁止硬编码"针对的是数据计算；该字段为空时输出空文本。
   > 🔄 **2026-10-03 修复**：源表空单元格经 pandas 读入为 `NaN`（既非 `None` 也非空串），
   > 原先的判空函数识别不到，导致拼接出字面量 "nan"（旧产物合并表 463 行全部为 "nan"）。
   > 已修正 `stat_engine._blank()` / `_text()` 识别缺失值，并在自检 R4 加入"无空值残留"断言。
2. **未回款原因分类为空时的表现**：任务2 输出空表。分类数由数据动态决定，
   与示例文件一致。若换成有分类的数据集，该表会自动生成数据行（本次交付数据集即 4 行）。
   分类列**不设条件格式**（`style_setting.reason_soft_cf=false`，跟随同行斑马纹）；
   启用该开关时才会按分类数生成等量的差异化柔和背景规则。
3. **运行环境的 Python 版本**：目标与验证环境均为 Python 3.11。
   代码已避免 3.10+ 专有语法（无 `match`、无 `X | Y` 类型联合、无 f-string 嵌套引号），
   `py_compile` 与 AST 扫描均通过；openpyxl 3.1.5 官方支持 3.11。
4. **LibreOffice 不是运行依赖**：缓存值注入用纯 Python 完成。
   `cached_values.py` 的 `recalc_with_soffice()` 只是开发期交叉验证的可选入口，缺环境自动跳过。

# 1. 部署依赖（Python 3.11；Windows 下用 python 代替 python3）
